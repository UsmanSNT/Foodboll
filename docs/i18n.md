# Localization

## Principles

- One app, one API, one database. Language changes **what is displayed**, never what exists: a Korean
  and an Uzbek user join the same match.
- Technical values (`PAYMENT_REVIEW`, `PLAYER`) are never translated. They map to catalog keys at render
  time (`PAYMENT_STATUS_LABEL_KEY` in `@foodboll/contracts`).
- No user-facing string lives in a component. ESLint enforces it.
- Language must never block a user: every localized field falls back instead of rendering empty.

## Three kinds of text

| Kind                                                                   | Where it lives                                                    | Who edits it             | Missing translation                        |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------ | ------------------------------------------ |
| UI chrome, errors, notifications                                       | `packages/i18n/src/catalog/{ko,uz}.ts` (typed, ICU MessageFormat) | developers / translators | compile error + test failure (cannot ship) |
| Shared football vocabulary                                             | `packages/i18n/src/glossary.ts`                                   | developers / translators | compile error                              |
| User-authored content (matches, payment instructions, legal documents) | `*_translations` tables, one row per language                     | organizers / admins      | fallback at read time                      |

### Catalog rules

- `ko.ts` defines the shape; `uz.ts` is typed `typeof ko`, so a missing/extra key does not compile.
  `MessageKey` is derived from it, so `t('match.aply')` does not compile either.
- Tests enforce: identical keys in all locales, identical ICU arguments, valid ICU syntax, no empty
  values, **no ASCII apostrophe** (it is an escape character in ICU). Uzbek uses `‘` (U+2018) for
  `o‘`/`g‘` and `’` (U+2019) for tutuq belgisi, matching the product copy.
- Dates and money are composed from catalog patterns (`format.dateTime`, `format.krw`) and always in
  `Asia/Seoul`. Platform `Intl` data for Uzbek is incomplete on some devices (months rendered as `M12`
  in a stock Chromium build), so it is not relied upon.

### Fallback for authored content

`pickLocalized(content, requested, sourceLanguage)` returns, in order: the reader's language, the
author's source language (the original), Korean, any other language. Blank strings count as missing.
Fallback is **per field**, and the API returns `{ text, locale, isFallback }` so clients can show
"원문(한국어)을 표시하고 있습니다." / "Asl matn (한국어) ko‘rsatilmoqda." and set `lang` correctly.

- Matches: `sourceLanguage` is mandatory and its translation must exist. Optional fields (description,
  rules, location instructions, equipment, cancellation policy) are independent.
- Payment instructions: bank name and instructions are per language; **account number and holder are
  stored once** (bank-registered values). Korean is required; the admin view lists
  `missingLanguages`. Changes insert a new row and deactivate the old one (history kept, one active row
  enforced by a partial unique index).
- Legal documents (`TERMS`, `PRIVACY`, `CANCELLATION`, `REFUND`): immutable versions.

## Registration and payment flow

Registration status (`APPLIED → CONFIRMED | CANCELLED`) and payment status
(`AWAITING_PAYMENT → PAYMENT_REVIEW → PAYMENT_CONFIRMED | PAYMENT_REJECTED → REFUNDED`) are technical
values; the UI shows `t(REGISTRATION_STATUS_LABEL_KEY[status])` / `t(PAYMENT_STATUS_LABEL_KEY[status])`.

- Applying to a paid match holds a seat for 24h (or until kick-off). No receipt in time → the seat is
  released lazily (before capacity is counted or lists are read); no background job is required.
  Seat allocation locks the match row, so capacity is never exceeded under concurrency.
- Free matches are confirmed immediately.
- Receipts: `PUT /v1/registrations/:id/receipt` with the raw file (JPEG/PNG/PDF, <= 5 MB). The type is
  detected from the file's bytes, files live outside the DB (`RECEIPT_DIR`, keys are server-generated),
  and downloads are owner/admin only with `no-store`, `nosniff` and a sandbox CSP.
- Admin rejects with a **reason code** (`AMOUNT_MISMATCH`, ...), never free text, so the player reads
  the reason in their own language. The notification is rendered with `localizedParams`.
- Status changes and their notifications are written in one transaction.

## Which language does a response use?

Server: `?lang=` > signed-in user's `preferred_language` > `Accept-Language` > Korean. `Content-Language`
and `Vary` are set on every response. Error bodies carry a stable `code` plus a localized `message`; the
web client localizes from `code` using its own catalog.

Client (`resolveLocale`): account choice > choice stored on device > device language > Korean.
Only an explicit choice is ever saved. A _detected_ or _default_ language shows the first-launch
screen (`언어 선택 / Tilni tanlang`) and is never persisted as a choice. After sign-in
`planLanguageSync` reconciles: account has no language → push the device choice; otherwise the
account wins on every device.

`users.preferred_language` is NULL until chosen. `users.device_locale` stores the raw tag the device
reports, for admin/support visibility only, and does not affect display. Admins see both
(`GET /v1/admin/users?language=ko|uz|none`). **There is no nationality column**: speaking Uzbek says
nothing about nationality. Add one only if a legal requirement appears and users supply it explicitly.

Notifications (`enqueueNotification`) render in the recipient's language at enqueue time (saved
choice, else device language, else Korean) and store the language used.

## Adding a language (e.g. `vi`)

1. `packages/i18n/src/locales.ts`: add the code to `LOCALE_CODES` and a descriptor to `LOCALES`.
2. `packages/i18n/src/catalog/vi.ts` (typed `typeof ko`) and register it in `catalog/index.ts`; add
   `vi` to every `GLOSSARY` entry. The compiler lists everything missing.
3. Write the `format.dateTime` / `format.krw` patterns.
4. New SQL migration: `INSERT INTO languages (...)` (set `enabled = false` until the translation has
   been reviewed). No schema change: all language columns reference `languages.code`.
5. `pnpm test`. A test asserts the seeded `languages` rows match the registry.

## Open items

- **Native review**: the Uzbek strings were written without a native-speaker review. Have a native
  speaker who plays football review `uz.ts` and `glossary.ts` before release.
- **Legal text** is not authored here. If a translation is missing, readers see the Korean original
  (flagged). Do not treat that as translated consent; get counsel's view on Terms/Privacy
  (Korean PIPA) and publish reviewed translations before launch.
- Uzbek written in Cyrillic (`uz-Cyrl`) is mapped to the Latin catalog.
- SMS: `‘`/`’` are not in the GSM-7 alphabet, so Uzbek SMS using them is sent as UCS-2 (shorter
  segments). Normalize to ASCII apostrophes in the SMS channel adapter when delivery is built.
- Search/matching of Uzbek names should normalize `'`, `‘`, `’`, `ʻ` to one form.
- Receipt storage is local disk (`LocalReceiptStorage`). Use object storage (implement
  `ReceiptStorage`) before running more than one API instance, and add malware scanning if required.
- Authentication is out of scope: the API verifies HS256 JWTs (`sub` = user id, `iss`/`aud` from
  config) issued by a future auth service and loads role/language from the database on each request.
